# テスト駆動で作る(tdd)

*原典は Matt Pocock の `tdd`(MIT ライセンス)。例を Python に置き換え、日本語化した。流れ全体の説明は ai-config の `ai-systems/dev-flow.md`。*

TDD は **RED(失敗するテストを書いて、失敗を確かめる)→ GREEN(通す最小の実装)** の繰り返し。この文書は、その繰り返しが「残す価値のあるテスト」を生むための決まり。毎サイクル、最初から最後まで当てはめる。

始める前に `GLOSSARY.md` と `docs/adr/` を読む。テスト名と関数名は用語集の言葉で付ける。

## 1. 良いテストとは

**外から見える振る舞いを、公開の入口から確かめる。中身(実装の詳細)は見ない。**中身を全部書き換えてもテストは変わらないのが正しい。良いテストは仕様書のように読める。「取消馬を除いて頭数を数え直す」と読めば何ができるかが分かり、作り替えても壊れない。

```python
# 良い: 振る舞いを確かめる
def test_取消馬を除いて頭数を数える():
    race = Race(runners=[h1, h2, h3], scratched=[h2])
    assert race.field_size() == 2

# 悪い: 中身を確かめる(作り替えると振る舞いが同じでも壊れる)
def test_field_sizeがfilterを呼ぶ(mocker):
    spy = mocker.spy(race_module, "_filter_scratched")
    Race(...).field_size()
    spy.assert_called_once()
```

悪いテストの見分け方: 内部の部品をモック(偽物に差し替え)している / 非公開の関数を直接呼ぶ / 呼ばれた回数や順番を確かめる / 名前が「何を」でなく「どうやって」/ 公開の入口を通らずに DB やファイルを直接覗いて確かめる。

## 2. 継ぎ目(seam): テストを置く場所

**継ぎ目** = 中を覗かずに振る舞いを見られる、公開の境界(関数・コマンド・API・出力ファイル)。テストは継ぎ目に置き、内部には置かない。

**事前に決めた継ぎ目にだけテストを書く。**仕様書(`docs/plans/<スラッグ>/spec.md`)の「継ぎ目」を使う。仕様書が無ければ、テストを書く前に継ぎ目を 1〜3 個書き出し、本人へ 1 行で見せてから進める(**返事待ちで止まらない**。違えば本人が言う)。全部はテストできない。継ぎ目を先に決めるのは、テストの手間を大事な道筋と込み入った計算に集めるため。

## 3. モックは外との境目だけ

偽物に差し替えてよいのは**外との境目**だけ: 外部 API・ネットワーク・時刻・乱数・(ときに)ファイルや DB。自分で書いたクラスや関数・内部の部品はモックしない。

外との境目は、引数で受け取る形にしておくと差し替えやすい。

```python
# 差し替えやすい
def fetch_odds(race_id, client):
    return client.get(f"/odds/{race_id}")

# 差し替えにくい
def fetch_odds(race_id):
    return requests.get(f"https://.../odds/{race_id}")
```

時刻は `datetime.now()` を中で呼ばず、引数で渡す(ai-config 系のリポジトリでは日本時間を `scripts/jst.py` から取る決まり)。

## 4. やってはいけない型

- **中身に縛られたテスト**: 第 1 節の悪い例
- **同語反復**: 期待値をコードと同じ計算で作る(`assert add(a, b) == a + b`)。必ず通るので何も確かめていない。**期待値は独立した出どころから**: 手で確かめた数字・具体例・仕様書・過去の実績値
- **横切り**: テストを全部先に書いてから実装を全部書く。想像の振る舞いを確かめることになり、実際の変化に鈍いテストになる。**1 テスト → 1 実装 → 次**の縦切りで、前のサイクルで分かったことを次のテストに活かす

## 5. 回し方の決まり

- **RED が先**: 失敗するテストを書き、**実際に走らせて失敗を確かめてから**実装する。最初から通るテストは何も確かめていない
- **GREEN は最小**: 通るだけの実装をする。次のテストを先取りしない。頼まれていない機能を足さない
- **1 サイクル 1 つ**: 継ぎ目 1 つ、テスト 1 つ、最小の実装 1 つ
- **作り直し(リファクタリング)はサイクルに入れない**: 全部 GREEN になってから、見直しの段階でやる(`/code-review` や `/simplify`)
- テストは 1 ファイルずつ頻繁に走らせ、最後に全体を 1 回走らせる。型チェック・lint(書き方の点検)があればそれも

## 6. データ分析・機械学習のコードでは

予想モデルや集計のように「正解が 1 つに決まらない」コードでも、確かめられる振る舞いはある。

- **リーク**(未来の情報が混ざること)が無い: 「発走時刻より後のデータを渡すと例外になる」
- **形と範囲**: 「確率の列は 0〜1、1 レースの合計が 1(誤差 1e-6)」
- **小さな手計算の例**: 3 頭・2 レースの手で作ったデータで、期待値を手で計算して書く
- **前と同じ結果**: 乱数の種を固定し、既知の入力で過去の出力と一致する(数字は過去の実行記録から取る)
