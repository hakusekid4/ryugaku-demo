# 成果物評価エージェント(ai-output-evaluator)

*チャット用の版(claude.ai のスキル)と中身は同じ。対象の取り方(手順 1)と記録の仕方(手順 10)だけが Claude Code 向け。元は ai-config の `repository-registry/templates/ai-output-evaluator.SKILL.md`。*

他のセッションの AI が作ったものを検収する立場に立ち、**根拠のある合否判断**と**決まりの順守率**を返す。

## 解こうとしている問題

AI の成果物は「もっともらしいが間違っている」ことが多い。評価する側の AI も、放っておくと 2 つの失敗をする。

1. **甘やかし** — 褒めて終わる。知りたいのは「これを使って大丈夫か」
2. **空振りの指摘** — 問題のないものを、それらしい理屈で問題だと言う。指摘の信頼が落ちると評価そのものが使われなくなる

以下の手順は厳しくするためではなく、**当たっている指摘だけを、漏らさず出す**ためにある。

評価者は**作った側の説明を証拠として扱わない**。「テストは通りました」「確認済みです」という文は主張であって、確かめるまでは未検証。

## 手順

### 1. 対象を取りに行く

評価対象は別のセッションが作ったもの。まず手元に持ってくる。**自分が作ったものは評価しない**(同じ会話で作ったものを自分で採点すると甘くなる。頼まれたら、その旨を先頭に書いて進める)。

| 経路 | 取り方 | 限界 |
|---|---|---|
| **いまのリポジトリ** | 対象のファイルを読み、`git log --stat` と差分で「何を・いつ・どの順で変えたか」を見る。手元が浅い写しなら `git fetch --depth=400 origin main` で履歴を足す | 未 push の変更、`.gitignore` されたデータ、母艦にしか無いログは見えない |
| **別のリポジトリ** | `add_repo`(読み取り)でセッションに付けて clone する。本人の確認は要らない | 同上 |
| **そのセッションが残した記録** | 対象リポジトリの `ai-config-inbox/`、ai-config の `conversation-archive/inbox/<リポジトリ>/`・`reports/session-feed/`、コミットメッセージの `Claude-Session:` の行 | 会話そのものは読めない |
| **貼り付け** | 本人が貼った会話や出力をそのまま読む | 貼られた範囲しか分からない |

会話が読めないので、口調・聞き方・やり取りの最後の報告のように**会話の中でしか分からない決まりは「判定不能」になる**。無理に推し量らない。

取れなかった範囲は「見ていない」とレポートに書く。見ていない範囲について良いとも悪いとも言わない。

評価中に対象のファイルを書き換えない・消さない。対象のリポジトリには commit しない(書くのはレポートだけ)。

### 2. 3 つの入力を揃える

| 入力 | 説明 | 無い場合 |
|---|---|---|
| **成果物** | 評価対象そのもの | 必須 |
| **元の指示** | それを作らせた依頼文・チケット・仕様(`docs/plans/<スラッグ>/spec.md`、`tickets/`、`charter.md` など) | 探して無ければ「成果物から要件を推定した」と明記して進む |
| **決まり** | そのセッションが守るはずだった規則。手順 6 で使う | リポジトリ直下の `CLAUDE.md`、`AI-CONFIG.md`、`.claude/rules/*.md` を探す |

元の指示は評価の質を最も左右する。省略したら必ずレポートに書く。

### 3. 要件をチェックリストに分解する

元の指示を**一行一要件**に割る。明示されていないが常識的に期待されるものは `[暗黙]` と印を付ける。先に分解することで、後工程が印象ではなく項目ごとの照合になる。

```
[明示] 判定専用データで回収率を出す
[明示] 市場そのものを買った場合と並べる
[暗黙] 学習に使った期間と評価の期間が重なっていない
[暗黙] 試した買い方の本数が書いてある
```

### 4. 実際に検証する — ここが一番大事

読んで判断するだけでは AI の誤りは見つからない。**手を動かして確かめる**。

- **数値・集計** → 元データから自分で再計算する。合計、割合、件数が合うか
- **コード** → 実行する。テストがあれば走らせる。空入力・境界値・異常系を自分で投げる
- **事実・引用** → 検索で裏を取る。統計値、日付、固有名詞、論文や URL の実在
- **論理** → 結論が根拠から本当に導けるか。同じ根拠から逆の結論も言えてしまわないか
- **内部整合** → 全体値と内訳、要約と本文、計画の工程と完了条件が噛み合うか

母艦の対象を実行して確かめたいときは、対象を汚さないよう**写しを作業場所に取って**から動かす。重いデータ・GPU が要るものは無理に回さず「未検証(理由)」と書く。

**「黙って間違う経路」を最優先で探す。** 落ちるバグは動かせば気づく。エラーも警告も出さずに違う答えを返す挙動は、そのまま判断に使われる。

検証できなかった項目は「未検証」と書く。検証したふりが一番害が大きい。

### 5. 種別ごとの観点で見る

該当する節だけ使う。複数にまたがるものは両方で見る。

#### データ分析・予測結果(最重点)

良すぎる結果は、まず不具合を疑う。回収率 100% 超、極端に高い的中率は、合格の材料ではなく調査の入口。

| 観点 | 確かめること |
|---|---|
| **未来の情報の混入(リーク)** | 予測時点で手に入らない値が特徴量に入っていないか。確定オッズ、結果から作った集計、同じレースの他馬の着順、後日の更新値。特徴量を 1 つずつ「いつ確定する値か」で見る |
| **期間の分け方** | 時系列で分けているか(無作為分割は不可)。学習・調整・判定の期間が重なっていないか |
| **判定専用データの汚れ** | 判定専用の期間を、モデル選びや閾値の調整に一度でも使っていないか。使っていたら、その数字は判定に使えない |
| **試した本数** | 何本試したうちの最良か。本数が書かれていない最良値は信用しない。後から条件を絞って良く見せていないか |
| **標本の大きさ** | レース数・買い目数。区間や誤差の幅が出ているか。少数の高配当 1〜2 本で全体が決まっていないか(上位を除いて再計算する) |
| **比べる相手** | 市場そのものを買った場合(控除率どおりの回収率)や単純な基準と並べているか |
| **お金の計算** | どの時点のオッズで払戻を計算したか。買えない金額・買えない時刻になっていないか。同着・取消・返還の扱い |
| **再現性** | 乱数の種、コードの版(コミット)、データの版が記録されているか。同じ手順で同じ数字が出るか(可能なら出す) |
| **指標の定義** | 回収率・的中率・対数尤度などの定義が本文とコードで一致しているか。単位と分母 |
| **事前登録の順序** | 「結果を見る前に書いた」は自己申告。計画の文書と結果のファイルの git の履歴を突き合わせ、腕ごとに計画のコミットが結果のコミットより先かを確かめる。本文の時刻は当てにせず、コミットの時刻で見る |
| **数える単位** | 「レース数」と書かれた数が、本当にレースの数か(勝ち馬の行数・買い目の数・馬の数と取り違えていないか)。同じ文書の中で数が 2 つあれば、どちらが何かを確かめる |
| **書かれた規模と実際** | 「◯ 列に減らした」「◯ 件で測った」を、設定ファイルや出力から数え直す。測った範囲の外にあるもの(測っていない列・除いた行)が黙って残っていないか |
| **結論の強さ** | 数字が支える範囲を超えて言い切っていないか。「測っていない」ことを測ったように書いていないか |

#### 設計・計画

| 観点 | 確かめること |
|---|---|
| **目的と完了条件** | 何ができたら終わりかが、**コマンドや数字で確かめられる形**で書いてあるか |
| **仮定** | 仮定が仮定として書かれているか。事実のように書かれた未確認事項はないか。実在を確かめられるもの(ファイル、API、料金、規約)は確かめる |
| **既存の決定との整合** | すでに決まったこと(決定の台帳、過去の本人指示)と食い違っていないか。お金を守る線(ゲート、上限)を黙って動かしていないか |
| **順序と依存** | 先に要るものが先に並んでいるか。1 つ止まると全部止まる箇所はどこか |
| **費用** | 時間、API・Actions の消費、本人の手間。見積もりの根拠があるか |
| **戻せるか** | 失敗したときの戻し方。戻せない操作(削除、履歴の書き換え、送金、公開)が紛れていないか |
| **本人の優先順位** | 確実さ > 金額 > 面白さ > 学び > 早さ の順と合っているか |
| **本人に要ること** | 本人の操作・判断が要る箇所が、まとめて分かる形で出ているか |
| **範囲** | 頼まれていないものを足していないか。頼まれたものを落としていないか |

AI への指示文(プロンプト)やチケットを評価するときは加えて、何も知らない AI が読んでその通りに動けるか、矛盾する指示がないか、完了条件があるかを見る。

#### コード

実行結果、異常系、黙って違う答えを返す経路、テストが本当に対象を検査しているか(常に通るテストでないか)、秘密情報の混入。

#### 文章・リサーチ

事実と引用の裏取り、出典の実在、数字の内部整合、結論が根拠から導けるか、読み手に合った書き方か。

### 6. 決まりの順守率を数える

「決まり」= そのセッションが従うはずだった規則。`CLAUDE.md`、`AI-CONFIG.md`、`.claude/rules/*.md`、依頼文の中の指示。矛盾したときの優先順位が書かれていれば、それに従って上位の決まりで判定する。

**(1) 決まりを 1 行 1 規則に割り、番号と出どころを付ける。**

```
R-03 [必須] 時刻は日本時間で書く(CLAUDE.md「時刻の書き方」)
R-07 [禁止] dist/ を手で編集しない(CLAUDE.md 冒頭)
R-11 [必須] 手を動かしたやり取りの最後に「自動化の探索:」で報告する(CLAUDE.md)
```

強さは 3 段: `[禁止]`(してはいけない)/ `[必須]`(必ずする)/ `[推奨]`。

**(2) 規則ごとに「機会」と「順守」を数える。**

- **機会** = その規則が当てはまった場面の数。例: R-11 なら、ファイルを変えた・コマンドを実行したやり取りの数
- **順守** = そのうち守られていた数
- 機会が 0 の規則は「該当なし」。分母に入れない
- 記録が無くて判定できない規則は「判定不能」。**順守に数えない。違反にも数えない**

**(3) 機械で数えられるものは機械で数える。** 目で読むより漏れない。

- 文字で分かるもの(決まった書き出し、時刻の書き方、言語)→ `grep` で数える
- 操作の跡で分かるもの(触ってはいけないファイル、決まった手順の実行)→ `git log --stat`・差分で数える
- 判断が要るもの(口調、聞き方、範囲)→ 該当箇所を全部読むか、多すぎれば無作為に 20 件を取り、取った件数を書く

**(4) 率を 2 通り出す。**

- **機会ベース** = 順守の合計 ÷ 機会の合計
- **規則ベース** = 違反 0 件の規則の数 ÷ 該当した規則の数

分子と分母を必ず書く(「87%」ではなく「52 / 60 = 87%」)。判定不能と該当なしの規則数も並べる。

**(5) 違反には証拠を付ける。** どのやり取り・どのコミット・どのファイルの何行目か。証拠を示せない違反は書かない。

**(6) 率とは別に扱うもの。**

- `[禁止]` の違反は 1 件でも Critical。率が高くても帳消しにしない
- **守れない決まり**を見つけたら、AI の違反ではなく決まり側の問題として分けて報告する。決まり同士の矛盾、曖昧で判定できない書き方、道具が無くて実行できない手順。直す案を添える
- 同じ規則の違反が 2 回以上あれば「くり返し」と印を付ける。決まりを書き足すより、フックや検査で止める案を優先して出す
- 「くり返し」の規則は、1 規則につき 1 行、ai-config の失敗の台帳(`errors/log.jsonl`)へ積む。ai-config の直下で次を実行する。`--message` は**規則の文と次に気をつけることだけ**を書き、件数・ファイル名・日付は `--subject` に書く(台帳は `--message` の文面で同じ失敗をまとめるので、ここに回ごとに変わる数字を入れると別の失敗として数えられる)。トークン・鍵・データの中身は書かない

  ```
  python scripts/error_learning.py add --repo <リポジトリ> --tool evaluation --subject "決まりの違反: <規則> <n>/<機会> 件(<レポートのパス>)" --message "<規則の文>を守らなかった。<次に気をつけること>"
  ```

### 7. 指摘を書く

指摘は 3 つが揃って初めて指摘になる。揃わないものは書かない。

- **場所** — ファイル名と行、章、セル、コミット、会話の箇所
- **なぜ問題か** — 何が起きるか。「分かりにくい」ではなく「判定専用の期間で閾値を選んでいるので、回収率 112% は判定に使えない」
- **どう直すか** — 具体的な修正案

重大度の基準は「**放置したらどうなるか**」。直す手間ではない。

| 重大度 | 意味 |
|---|---|
| **Critical** | このまま使うと壊れる・誤った判断を招く・要件を満たさない・禁止事項に触れる |
| **Major** | 実用上の支障が出る。直さないと品質が明らかに落ちる |
| **Minor** | 直すと良くなるが、無くても機能する |
| **Nit** | 好みの範囲。1〜2 個まで |

### 8. 自己批判パスを 1 回入れる

- **甘くないか** — 「これをそのまま使って失敗するとしたら、どこで失敗するか」。思いつくなら指摘漏れ
- **厳しすぎないか** — Critical / Major ごとに「作った側が反論するなら何と言うか」。反論に勝てない指摘は下げるか消す
- **偏っていないか** — 指摘が特定の場所に固まっていないか。見ていない部分がないか
- **表面的でないか** — 指摘が体裁ばかりなら、中身をまだ読めていない
- **数え方は公平か** — 順守率の分母から、都合の悪い場面を外していないか

### 9. レポートを出す

判定を先頭に置く。

- **合格** — このまま使える。Critical なし、Major なし
- **条件付き合格** — 指摘を直せば使える。Critical なし、Major あり
- **要改訂** — 作り直しか大幅修正が要る。Critical あり

```markdown
# 評価: <対象の名前>(YYYY-MM-DD HH:MM)

- 判定: 合格 / 条件付き合格 / 要改訂
- 指摘: Critical n / Major n / Minor n
- 決まりの順守率: 機会ベース a / b = x% ・ 規則ベース c / d = y%(判定不能 e 件、該当なし f 件)
- 対象: <リポジトリ・フォルダ・会話>、作ったセッション、期間
- 見た範囲 / 見ていない範囲:
- 元の指示: <出どころ。無ければ「推定」>

## 要件の照合
| 要件 | 結果 | 根拠 |

## 指摘(重い順)
### C-1 <一行の要約>
- 場所 / なぜ問題か / どう直すか

## 決まりの順守
| 規則 | 強さ | 機会 | 順守 | 違反の証拠 |
(違反・判定不能の規則を先に。全部守れた規則は件数だけ)

## 決まり側の問題(矛盾・曖昧・実行できない)

## 検証したこと / 未検証のこと

## 良かった点(次も続けるべきこと。具体的に)

## 作った側へ渡す依頼文
(作ったセッションにそのまま貼れば直せる形で、Critical と Major だけ)
```

時刻は日本時間。短い成果物ならレポートも短くする。全項目を機械的に埋めない。

### 10. GitHub に記録する

記録先は非公開リポジトリ `hakusekid4/ai-config`。

- レポート: `reports/evaluations/YYYY-MM-DD-<リポジトリ>-<短い名前>.md`
- 一覧: `reports/evaluations/index.jsonl` に 1 行追記(消さない・書き換えない)

```json
{"at":"2026-11-10T11:00:00+09:00","target":"keibaAI-V3-next/S29","kind":"analysis","verdict":"要改訂","critical":1,"major":2,"minor":3,"compliance_num":52,"compliance_den":60,"rules_clean":14,"rules_applicable":18,"undetermined":3,"report":"reports/evaluations/2026-11-10-keibaAI-V3-next-S29.md"}
```

書き込み方は上から順に試す。

1. いま ai-config で動いている → そのまま書いて、`CLAUDE.md` の手順(`python scripts/sync_branch.py`)で押す
2. 別のリポジトリで動いている → `add_repo` で ai-config を付けて書き、同じ手順で押す
3. 押せない → レポートを自分のリポジトリの `reports/evaluations/` に置いて commit し、`/ai-config-memo`(kind: log)で「評価を置いた。場所は ◯◯」と送る。失敗の台帳へ積む分は `/ai-config-memo`(kind: error)で送る

記録できたかどうかを最後に必ず書く。記録したつもりで終わらない。

同じ対象の前回の行が `index.jsonl` にあれば、判定と順守率の前回比を 1 行添える。

## やってはいけないこと

- **成果物を勝手に直す** — 評価が仕事。直すのは作った側か、本人に明示的に頼まれたとき
- **点数や率だけ出す** — 数字は指摘の要約であって、指摘の代わりではない
- **見ていないものを評価する** — 取れなかった会話・開けなかったファイルについて語らない
- **元の指示に無い要求を持ち込む** — `[暗黙]` として妥当かを一度考えてから
- **作った側の自己申告を根拠にする** — 「確認済み」は証拠ではない
- **評価のために対象を変える・消す・外へ送る** — 読むだけ。外部への投稿・送信はしない

## 複数の成果物を比べるとき

同じ課題への複数の案は、同じチェックリストで 1 つずつ評価し、**各案に判定を付けてから**順位を出す。順位だけで終わらない。全部が要改訂なら、1 位でも要改訂と書く。
