# 計画を詰める(grill-with-docs)

*原典は Matt Pocock の `grill-with-docs`(`grilling` + `domain-modeling`、MIT ライセンス、github.com/mattpocock/skills)。本人の決まり(日本語・確認は束ねて出す・「任せる」で止まらない)に合わせて書き直した。流れ全体の説明は ai-config の `ai-systems/dev-flow.md`。*

## これは何か

作る前に、決めるべきことを**木**(決定木。ある決定が決まると、その下にぶら下がる決定が聞けるようになる)として洗い出し、**聞ける問だけを 1 ラウンドにまとめて**出す。答えが返るたびに木を広げ、聞くことが無くなったら終わり。途中で決まった用語と設計判断は、その場でファイルに書く。

`/new-project`(新しい取り組みを**やるかどうか・何のため**かの 1 問 1 答)とは別物。こちらは**やると決まったものを、どう作るか**を詰める。新しいプロジェクトなら先に `/new-project` で企画書(`charter.md`)を作り、その「最初の 3 手」の 1 つをここで詰める。

## 置き場(このリポジトリの中)

| ファイル | 中身 | いつ書くか |
|---|---|---|
| `docs/plans/<スラッグ>/grill.md` | ラウンドごとの問・推奨・答え・仮置き | **1 ラウンドごと**(会話が切れても再開できるように) |
| `GLOSSARY.md`(リポジトリの直下) | 用語集。この取り組み固有の言葉だけ | 用語が 1 つ決まった**その場で** |
| `docs/adr/NNNN-<スラッグ>.md` | 設計判断の記録(ADR) | 第 4 節の 3 条件がそろったときだけ |

スラッグは英小文字・数字・ハイフン(例: `late-money-feature`)。**ファイルは要るときに初めて作る。**用語集も ADR も、最初の 1 件が決まるまで作らない。

## 1. 始める前に(事実は AI が集める)

1. `GLOSSARY.md`(無ければ `GLOSSARY-MAP.md`)と `docs/adr/` を読む。無ければ黙って進める
2. `docs/plans/<スラッグ>/grill.md` が既にあれば、**続きから**再開する。最初から聞き直さない
3. 関係するコード・README・企画書・台帳を読む。**調べれば分かる事実は本人に聞かない。**時間がかかる調べものは作業係(サブエージェント)に出し、その結果に依存しない問は先に出す

## 2. ラウンドの出し方

- **前線**(frontier)= 前提がすべて決まっていて、いま聞ける問。前線の問を**まとめて 1 ラウンド**で出す(1 ラウンド最大 5 問。多ければ影響の大きい順に 5 問)
- 他の問の答え次第で変わる問は、**次のラウンドへ回す**
- 各問に**推奨の答え**を付け、選択肢には必ず「決めていない / 任せる」を入れる
- **「任せる」が返ったら推奨で決め、`仮:` を付けて記録し、先へ進む。そこで止まらない**
- 本人が「もういいから作って」と言ったら、残りは推奨で仮置きして終える

形(日本語で、この形を崩さない):

```
**Q1 <問の題>**: <問の本文。選択肢 A / B / C / 任せる>
→ 推奨: <推奨の答え>(理由 1 行)

---

**Q2 <問の題>**: ...
→ 推奨: ...
```

返答の終わりに「全部推奨でよければ『任せる』の一言でいい」と添える。

## 3. 用語を詰める(用語集)

- 本人の言葉が用語集とぶつかったら、**その場で指摘する**。「用語集では『締切直前』は発走 10 分前以内だが、いまの話は 3 分前のこと?」
- あいまいな言葉・1 語に 2 つの意味がある言葉は、正確な言葉を提案する。「『モデル』は予想モデルのこと? 賭け方 AI のこと?」
- 境界を試す**具体的な場面**を AI が作って聞く(例: 「取消が出て頭数が変わったレースはどう数える?」)
- 本人の説明とコードが食い違ったら、それを示す。「コードは〇〇を全部捨てているが、いまの話では一部残すはず。どちらが正しい?」
- 用語が決まったらその場で `GLOSSARY.md` に書く。形:

```md
# <この取り組みの名前>

<何のための領域か 1〜2 文>

## 用語

**締切直前**:
発走前 10 分以内の時点。オッズが最終に近づく区間。
_使わない_: 直前、ラスト、late

**持ち時計**(`best_time`):
その馬が同じ距離で過去に出した最速の走破時計。
_旧称_: K01
```

- **定義は 1〜2 文。何であるかを書き、どう実装するかは書かない**(用語集は仕様書でもメモ帳でもない)
- この取り組みに固有の言葉だけ載せる。一般的なプログラミング用語は載せない
- 同じものに複数の名前があれば 1 つに決め、他は `_使わない_` に並べる。番号から名前に付け替えたものは `_旧称_` を残す
- コード・列名で使う英語名があれば括弧で添える

## 4. 設計判断を残す(ADR)

次の 3 つが**全部**そろったときだけ ADR を書く。1 つでも欠けたら書かない。

1. **戻しにくい**: 後で考えを変えると、それなりの手間がかかる
2. **背景なしでは意外**: 後から読んだ人が「なぜこうした?」と思う
3. **本当の比較があった**: 他の案があり、理由があって選んだ

形(1 段落でよい。番号は `docs/adr/` の最大番号 + 1):

```md
# 0003 <決めたことの短い題>

<背景・決めたこと・理由を 1〜3 文>
```

必要なときだけ「状態(提案 / 採用 / 廃止 / 0007 で置換)」「比べた案」「後で効いてくること」を足す。既存の ADR と矛盾する案が出たら、黙って上書きせず「ADR-0002 と食い違うが、〇〇なので見直す価値がある」と明示する。

## 5. 記録(grill.md)

ラウンドごとに追記する。

```md
## ラウンド 2(2026-10-05 21:30)

| Q | 問 | 答え | 備考 |
|---|---|---|---|
| Q1 | 締切直前の窓 | 発走 3〜1 分前 | |
| Q2 | 取消の扱い | 仮: 取消馬を除いて頭数を数え直す | 任せる → 推奨で仮置き |

次の前線: 払戻の端数の扱い / 検証期間
```

## 6. 終わり方

- 前線が空になったら(全部の枝を見て、黙って仮定したものが無い)、決まったことを 5〜10 行で要約して出す
- **本人が「それでいい」と言うまで、実装に入らない。**次は `/to-spec` で仕様にまとめる
- 本人の判断が必要だが今は決められないものは、その場で追撃せず ai-config の台帳(`ai-systems/open-decisions.md`。ai-config 以外からは `/ai-config-memo` の `kind: question`)へ積む

## しないこと

- 調べれば分かる事実を本人に聞く
- 前のラウンドの答え次第で変わる問を、同じラウンドに混ぜる
- 用語集に実装の詳細・ファイルパス・コードを書く
- 何でも ADR にする(3 条件を満たさないものは書かない)
- 詰め終わる前にコードを書き始める(調査はしてよい)
