# 仕様にまとめる(to-spec)

*原典は Matt Pocock の `to-spec`(旧名 `to-prd`、MIT ライセンス)。本人の決まりに合わせて日本語化し、置き場をこのリポジトリ内の Markdown にした。流れ全体の説明は ai-config の `ai-systems/dev-flow.md`。*

**本人に聞き取りはしない。**会話とコードから分かっていることをまとめるだけ。足りないところは `仮:` と書いて進める。

## 手順

1. **読む**: `GLOSSARY.md`・`docs/adr/`・`docs/plans/<スラッグ>/grill.md`・関係するコード。仕様の言葉は用語集に合わせ、ADR に反しない
2. **継ぎ目(seam)を決める**: 継ぎ目 = テストで振る舞いを外から確かめる境界(関数・コマンド・API・出力ファイルなど、中を覗かずに結果を見られる所)
   - 既にある継ぎ目を優先する。新しく作るなら、なるべく外側(高い位置)に。**少ないほどよい。理想は 1 つ**
   - 推奨の継ぎ目を仕様に書き、本人には要約の最後で 1 行で見せる(「継ぎ目は `python -m rail.judge` の出力 JSON にした。違えば言って」)。**返事を待って止まらない**
3. **書く**: 下の型で `docs/plans/<スラッグ>/spec.md` に書く。状態は `ready-for-agent`(AI が着手してよい)
4. **出す**: 本人へは 3〜5 行の要約とファイルの場所だけ。次は `/to-tickets`

## 型

```md
# <題>

- 状態: ready-for-agent
- 作成: 2026-10-05 21:40(JST)
- 元: docs/plans/<スラッグ>/grill.md / 企画書 projects/<スラッグ>/charter.md など

## 困りごと
本人(または使う人)から見た問題。

## 解決
本人から見た解決のしかた。

## できるようになること(ユーザーストーリー)
番号付きで、漏れなく長めに並べる。形は「<誰>として、<何>がしたい。<なぜなら>」。
1. 本人として、毎朝のレース一覧で締切直前に売れた馬が分かるようにしたい。買う前に見落とさないため
2. ...

## 実装の決めごと
- 作る / 直すまとまり(モジュール)と、その外から見た形(入出力)
- 構造・データの形・外部との約束
- 本人から出た技術的な注文
- 継ぎ目: <どこで確かめるか>

**ファイルパスやコードは書かない**(すぐ古くなる)。
例外: 試作で決まった型・状態の遷移・データの形など、文章より正確に決めごとを表せる断片は、要る部分だけ載せて「試作から」と注記する。

## テストの決めごと
- 良いテストの条件: 中身ではなく外から見える振る舞いだけを確かめる
- どのまとまりを、どの継ぎ目でテストするか
- 手本にする既存のテスト

## やらないこと
この仕様の範囲外。

## 仮で置いたもの
`仮:` で決めたものと根拠。後で本人が覆せるように 1 行ずつ。

## その他
```

## しないこと

- 新しく問を立てて聞き取りを始める(足りなければ `仮:`)
- 継ぎ目の確認待ちで止まる
- ファイルパス・コード片を本文に並べる
